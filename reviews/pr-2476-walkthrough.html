Preserve OCI image user identity

A reviewer walkthrough of OpenShell PR #2476 - feat(sandbox): honor OCI image user identity

Issue #2331 · base main ← head mgrossman/image-user-identity

Docker + Podman non-root agent fail-closed handshake 23 implementation/docs files
TL;DR. Docker and Podman now preserve a sandbox image's non-root OCI USER for the agent children, while deliberately starting the OpenShell supervisor as 0:0. The supervisor resolves the image declaration against the exact inspected image filesystem, persists that numeric identity, reports it to the gateway, and waits for an exact protocol acknowledgement before launching user code. Operators can select an explicit fixed UID/GID instead when external storage requires a stable principal. The implementation treats image identity as a cross-component security protocol, not as trusted environment configuration.

1. Problem and invariant

A community image may already define the correct non-root application user. OpenShell needs to use that identity without surrendering the privileges required to establish the sandbox boundary.

Prior mismatch

The local runtime overrides the image entrypoint with openshell-sandbox. If it also ignores OCI USER, the eventual agent can run under an identity unrelated to the image's ownership model.

New invariant

The supervisor starts as root, but every direct or SSH-launched agent child uses one gateway-validated, persisted, non-root numeric identity derived from the selected immutable image or fixed operator config.

Non-goal. This does not run agent code as root and does not make Dockerfile USER control the supervisor. Root exists only in the trusted supervisor process so it can prepare namespaces, mounts, ownership, policy enforcement, relay sockets, and the final privilege drop.

2. The identities in one sandbox

Container engine

Docker or rootless Podman creates the workload and owns host/user-namespace mappings.

Supervisor: 0:0

Trusted OpenShell control process. The driver explicitly overrides OCI USER for this process.

Agent: image or fixed ID

Untrusted requested command. It gets the resolved UID/GID, no supplementary groups, and sandbox policy.

3. Image and fixed modes

ModeIdentity sourceAccount recordsExternal storage
image (default)Immutable image ID plus raw OCI Config.User.Required only when a name or implicit primary group must be resolved.Creator-selected bind and named-volume mounts are rejected.
fixedOperator-configured fixed_uid and fixed_gid.Not required; both IDs are already numeric.Allowed subject to existing mount and bind-enable checks.

Docker pins container creation to the inspected image ID. Podman inspects the selected result, then creates with pull policy never and that immutable ID. A mutable tag cannot change between identity inspection and root filesystem selection.

Why fixed mode exists. An image-selected UID is local to that image's ownership assumptions. Shared or host storage needs an operator-controlled principal whose ownership contract exists outside the image, so the two concerns are represented as explicit modes.

4. End-to-end startup flow

  1. The gateway records intent. Creating a Docker or Podman sandbox persists managed_identity_required = true. Creator-supplied run_as_user and run_as_group are rejected.
  2. The driver selects an immutable rootfs. It pulls or resolves the requested image, inspects its immutable ID and OCI Config.User, and validates the selected identity mode.
  3. The driver starts only the supervisor as root. It overrides the runtime user to 0:0, appends --managed-local-identity, and injects protected source/image metadata after image and request environment values.
  4. The supervisor verifies two independent authorities. The driver argv assertion must exactly agree with the gateway's persisted marker. Either mismatch aborts startup.
  5. The supervisor resolves and persists identity. It safely parses image account files when needed, rejects root or malformed inputs, and binds the record to image ID and source inputs in /var/lib/openshell/agent-identity.json.
  6. The local SSH target binds first. This creates the root-only Unix socket needed by later relay requests, but no remote relay is exposed and no user child exists yet.
  7. The gateway validates the handshake. SupervisorHello reports the resolved record. The gateway validates and atomically persists it, queues SessionAccepted, then publishes the session to relay callers.
  8. The supervisor requires an exact acknowledgement. User code launches only when resolved_identity_version exactly equals the version it reported.
  9. The child drops privilege. The parent prepares all fallible identity state before fork; the child clears groups, calls numeric credential syscalls, applies sandboxing, and execs the command.

6. OCI USER resolution

Image mode accepts the common OCI forms, then converts them to one numeric UID/GID pair.

OCI Config.UserResolutionAccount-file requirement
appLook up user and use its primary GID./etc/passwd
1001Use UID; look up its primary GID.Matching passwd row
app:workersLook up user and group independently./etc/passwd and /etc/group
1001:1002Use both numeric values directly.None

The parser opens bounded regular account files without following symlinks and does not invoke NSS for image identity resolution. Empty, malformed, missing, ambiguous, control-character-containing, or root-resolving values fail startup. OpenShell does not create users or rewrite the image's account database.

identity record = {
  version: 1,
  source: "image" | "fixed",
  immutable_image_id: "...",
  image_user: "app:workers" | null,
  uid: 1001,
  gid: 1002,
  supplementary_gids: []
}

7. Safe child privilege drop

The code deliberately minimizes work between fork and exec, where allocator, lock, and NSS activity is unsafe in a multithreaded process.

Parent, before fork

Resolve named credentials and NSS state, validate namespace UID/GID maps, compute supplementary-group transition, prepare child environment, and validate all fallible identity inputs.

Child, after fork

Apply only precomputed direct syscalls: clear and verify supplementary groups, call setgid, call setuid, clear the capability bounding set, apply sandbox restrictions, and exec.

Direct and SSH parity. The initial entrypoint and every SSH child use the same prepared credential model. Managed children receive HOME=/sandbox, numeric presentation variables where appropriate, and no supplementary groups.

Filesystem preparation changes ownership only on the /sandbox directory itself. It does not recursively chown image content or nested mounts. Missing final writable directories use descriptor-relative no-follow operations to reject symlink races.

8. Two-signal readiness

A running container is not sufficient: managed sandboxes are Ready only when the runtime and the identity-authenticated supervisor session are both ready.

Runtime readySession acceptedPublic phaseMeaning
NoNoProvisioningContainer and identity channel are still starting.
YesNoProvisioningContainer runs, but identity has not been accepted.
NoYesProvisioningSession arrived first; runtime has not independently reported ready.
YesYesReadyBoth independent dependencies are satisfied.

SandboxStatus.runtime_ready persists the compute signal so either event order works. Docker emits an explicit RuntimeReady condition. Drivers without that condition retain a phase-based fallback. Terminal Error and Deleting states remain authoritative and cannot be promoted by a connected supervisor session.

Read-only access does not make external storage safe for an arbitrary image-selected principal. The restrictions are therefore scoped to Docker/Podman managed identity mounts. Kubernetes mount validation and identity behavior remain unchanged.
