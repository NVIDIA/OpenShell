# Principal engineer review findings: PRs 5082, 5083, and 5084

Each PR received a separate static review of its complete diff against its immediate stack base. No tests were run. No GitHub comments were posted.

## PR #5082: HTTP export failures can appear successful

[PR #5082](https://github.com/NVIDIA/OpenShell/pull/5082) adds OTLP HTTP/protobuf export. Reviewed head: `0d79a30690a1cc366d5477ef02d0d866298a4a12`.

Before this PR, the gRPC export path propagated incomplete-response transport errors. The new HTTP client replaces response-body collection errors with an empty body while preserving HTTP 200. A collector that sends success headers and then resets or truncates its response can therefore appear to have acknowledged the batch. An oversized partial-success response can also lose its rejection information.

The SDK accepts an empty protobuf response as success, so operators can see exported OCSF counters increase without retries or loss reporting for that failure.

Recommendation: propagate body collection errors instead of synthesizing an empty successful response.

[Affected code: crates/openshell-otel/src/transport.rs, lines 96–100](https://github.com/NVIDIA/OpenShell/blob/0d79a30690a1cc366d5477ef02d0d866298a4a12/crates/openshell-otel/src/transport.rs#L96-L100).

## PR #5083: Configuration errors can expose collector credentials

[PR #5083](https://github.com/NVIDIA/OpenShell/pull/5083) adds configured collector headers. Reviewed head: `be0c7129e8dc83cc3af8962731acb68be73ac873`.

Before this PR, collector credentials came from environment variables, outside TOML diagnostics. The new inline header configuration allows secrets into TOML source excerpts. For example:

```toml
headers = { authorization = 'Bearer example-secret', x-tenant = 42 }
```

The numeric value fails deserialization of the new string-valued header map. The loader preserves the complete TOML error, and startup diagnostics display the offending source line, exposing the authorization token. Redacted Debug output and value-free validation messages do not protect this earlier failure path.

Recommendation: sanitize parser diagnostics before displaying them, retaining location and error category without source excerpts or secret-bearing messages.

[Affected code: crates/openshell-server/src/config_file.rs, line 677](https://github.com/NVIDIA/OpenShell/blob/be0c7129e8dc83cc3af8962731acb68be73ac873/crates/openshell-server/src/config_file.rs#L677). Supporting path: `parse_and_validate` in the same file at line 1237 preserves the error; `crates/openshell-server/src/cli.rs:405` displays it.

## PR #5084: Accepted TLS configuration can prevent sandbox creation

[PR #5084](https://github.com/NVIDIA/OpenShell/pull/5084) adds custom collector CAs and client certificates. Reviewed head: `f24def89ed944b3ddd16a258145b42a0c140b917`.

Before this PR, TLS certificate material was absent from sandbox launch registrations. The new implementation copies complete PEM material separately into each enabled signal's authentication bundle, even when all three signals inherit the same collector.

Each TLS file is accepted up to 64 KiB, but shared-supervisor registrations have a 256 KiB total limit. For example, a valid 64 KiB CA bundle, 32 KiB certificate chain, and 2 KiB key inherited by traces, OCSF, and agent export produce roughly 294 KiB before JSON overhead. Gateway configuration succeeds, but subsequent shared Kubernetes sandbox creation fails with `sandbox instance launch material is too large`.

Recommendation: deduplicate inherited material or validate the aggregate against its downstream limit before accepting configuration.

[Affected code: crates/openshell-server/src/otel_tracing.rs, lines 345–349](https://github.com/NVIDIA/OpenShell/blob/f24def89ed944b3ddd16a258145b42a0c140b917/crates/openshell-server/src/otel_tracing.rs#L345-L349). Supporting paths: `crates/openshell-otel/src/tls.rs:107–114`, `crates/openshell-driver-kubernetes/src/driver.rs:3829–3875` and `:5718`, and `crates/openshell-supervisor-control/src/registration.rs:182–190`.
