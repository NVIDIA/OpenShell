Register your middleware service in gateway configuration, then attach it to destination hosts in sandbox policy. This page also covers ordering, failure behavior, service lifecycle, and observability. Built-in middleware needs only a policy entry.

## Use Your Own Middleware Service

A middleware service is a gRPC server that implements the supervisor middleware protocol. The [content guard example](https://github.com/NVIDIA/OpenShell/tree/main/examples/supervisor-middleware-content-guard) implements request, response, and WebSocket checks in one service, and includes a policy and a local launcher.

To use your own service:

1. Start the service where both the gateway and sandbox supervisors can reach it.
2. Register it in gateway configuration.
3. Restart the gateway.
4. Attach it in sandbox policy by setting `middleware` to the registration `name`.

Register the service in gateway TOML:

```toml
[[openshell.supervisor.middleware]]
name = "content-guard"
grpc_endpoint = "https://content-guard.example:50051"
tls_ca_cert_path = "/path/to/content-guard-ca.pem"
max_payload_bytes = 262144
timeout = "500ms"
```

<ParamField path="name" type="string" required={true}>
  Unique name that policies use to attach the service. The `openshell/` prefix is reserved for built-ins.
</ParamField>

<ParamField path="grpc_endpoint" type="string" required={true}>
  Service address reachable from the gateway and sandbox supervisors.
</ParamField>

<ParamField path="max_payload_bytes" type="integer" required={true}>
  Largest payload the service inspects. For a complete HTTP body, it limits the body and the replacement separately. For a streamed HTTP body, it limits each chunk, and OpenShell also caps chunks at 64 KiB. For WebSocket, it limits each text message and its replacement. Must be at most 4 MiB and no larger than the service advertises. Set it to `0` only when every binding the service advertises is a version 2 HTTP binding that supports no body modes.
</ParamField>

<ParamField path="timeout" type="string" default="500ms">
  Time limit for `Describe`, `ValidateConfig`, and each middleware exchange. Use an integer followed by `ms` or `s`, from `10ms` through `30s`. A binding may advertise a shorter timeout. For HTTP, it applies to opening a stream and its preflight, and to each complete-body or legacy exchange. For WebSocket, it applies to the preflight, capped at 1 second, and to each message. Chain, body, and stall deadlines apply separately, as listed in [Limits](/extensibility/supervisor-middleware/operations#limits). Streamed HTTP bodies and WebSocket connections have no total deadline.
</ParamField>

<ParamField path="tls_ca_cert_path" type="string">
  Private CA for the service certificate. Without it, OpenShell uses platform trust roots.
</ParamField>

<ParamField path="audience" type="string" default="urn:openshell:extension:middleware:<name>">
  Token audience. Refer to [Authenticating Extensions](/extensibility/overview#authenticating-extensions).
</ParamField>

<ParamField path="allow_insecure_transport" type="boolean" default="false">
  Allows a plaintext `http://` endpoint with no authentication. Use it for local development or on a network that already authenticates callers.
</ParamField>

At startup, the gateway contacts every registered service to read its capabilities and verify [protocol compatibility](/extensibility/overview#protocol-negotiation). The gateway does not start if a service is unavailable or incompatible. [Gateway Configuration](/how-it-works/gateways/configuration#supervisor-middleware-services) describes the full TOML context.

When the gateway has JWT signing configured, OpenShell authenticates every call to your service with a short-lived token. [Authenticating Extensions](/extensibility/overview#authenticating-extensions) describes how your service validates it.

## Attach Middleware in Policy

Add entries to the top-level `network_middlewares` map in sandbox policy. Each entry selects destination hosts and names the middleware to run for them:

<Tabs>
<Tab title="Middleware service">

Attach a [registered service](#use-your-own-middleware-service) by its registration name. Your service defines and validates the `config` object:

```yaml showLineNumbers={false}
network_middlewares:
  content-guard:
    middleware: content-guard
    config:
      mode: redact
      terms: ["internal-only"]
      replacement: "[FILTERED]"
    endpoints:
      include: ["api.example.com"]
```

</Tab>
<Tab title="Multiple middleware">

Run two middleware for the same hosts. `regex-demo` runs before `content-guard` because it has the lower `order`, and neither runs for `trusted.example.com`:

```yaml showLineNumbers={false}
network_middlewares:
  regex-demo:
    middleware: openshell/regex
    order: 10
    endpoints:
      include: ["*.example.com"]
      exclude: ["trusted.example.com"]
  content-guard:
    name: Content guard
    middleware: content-guard
    order: 20
    endpoints:
      include: ["*.example.com"]
      exclude: ["trusted.example.com"]
```

</Tab>
<Tab title="Built-in">

Attach the built-in `openshell/regex` middleware to one host:

```yaml showLineNumbers={false}
network_middlewares:
  regex-demo:
    middleware: openshell/regex
    endpoints:
      include: ["api.example.com"]
```

<Note>

`openshell/regex` is a regex redactor used for demonstration only. It lets you try middleware without running your own service. It replaces text that matches a fixed `sk-` pattern in UTF-8 HTTP bodies and outgoing WebSocket text messages, and the pattern is not configurable. Do not rely on it to detect or remove sensitive data.

</Note>

</Tab>
</Tabs>

### Entry Fields

The map key, such as `content-guard`, is the entry's stable identity in logs. Each entry accepts these fields:

<ParamField path="middleware" type="string" required={true}>
  A built-in middleware name, such as `openshell/regex`, or the `name` of a registered service.
</ParamField>

<ParamField path="endpoints.include" type="string[]" required={true}>
  Destination hosts to run the middleware for. Uses the same host patterns as network policy endpoints.
</ParamField>

<ParamField path="endpoints.exclude" type="string[]">
  Destination hosts to skip. Takes precedence over `include`.
</ParamField>

<ParamField path="order" type="integer" default="0">
  Position in the chain when several entries match the same host. Lower values run first. Values must be unique within a policy, so set them explicitly when a policy has more than one entry.
</ParamField>

<ParamField path="on_error" type="'fail_closed' | 'fail_open'" default="fail_closed">
  What happens when the middleware fails. Applies to WebSocket bindings and to HTTP bindings that use the deprecated HTTP protocol 1. HTTP bindings that use HTTP protocol 2 always fail closed. Refer to [Choose Failure Behavior](#choose-failure-behavior).
</ParamField>

<ParamField path="on_uninspectable" type="'deny' | 'allow'" default="deny">
  What happens to selected traffic that no middleware can inspect. Refer to [Handle Uninspectable Traffic](#handle-uninspectable-traffic).
</ParamField>

<ParamField path="config" type="object">
  Configuration passed to the middleware. The middleware defines and validates its format.
</ParamField>

<ParamField path="name" type="string">
  Display name. Defaults to the map key.
</ParamField>

[Policy Schema](/how-it-works/policies/schema#network-middleware) lists every field and limit.

## Choose Failure Behavior

Middleware fails when it cannot complete its check, for example when its service is unavailable, times out, returns an invalid result, or receives a payload over its limit. By default, OpenShell blocks the affected request, response, or WebSocket connection.

How OpenShell handles a failure depends on the binding. Each HTTP binding in a service's manifest uses one of two [HTTP protocols](/extensibility/supervisor-middleware/operations#http-protocols):

- HTTP bindings that use HTTP protocol 2 always fail closed. If the middleware fails before OpenShell forwards the request or starts sending the response, the sandbox receives an error response. If it fails after OpenShell has sent part of the request upstream or part of the response to the sandbox, OpenShell aborts the connection. OpenShell never skips a failed version 2 stage, retries it, or recovers the original body.
- WebSocket bindings, and HTTP bindings that use the deprecated HTTP protocol 1, follow the entry's `on_error` field. `fail_closed`, the default, blocks the traffic. `fail_open` skips the failed middleware and lets the traffic continue.

<Warning>

`fail_open` skips failed middleware and lets the traffic continue. Avoid it unless availability matters more than enforcement for that traffic. OpenShell emits a detection finding each time it skips middleware. OpenShell 0.2.0 removes HTTP protocol 1, so `fail_open` then applies only to WebSocket bindings.

</Warning>

When you create a sandbox or update a policy, the gateway rejects `on_error: fail_open` on an entry whose middleware requires HTTP protocol 2, whatever its bindings and `on_uninspectable` say. Supervisors that predate HTTP protocol 2 cannot run such a service, so they would skip it for HTTP and WebSocket traffic alike. To keep `fail_open` for a WebSocket binding, deploy a build of the service that serves both HTTP protocols, which does not require HTTP protocol 2. OpenShell 0.2.0, which needs current supervisors, accepts `fail_open` for the WebSocket bindings of such middleware again.

The gateway also rejects `on_error: fail_open` on an entry that sets `on_uninspectable: deny` if its middleware has neither a WebSocket binding nor an HTTP protocol 1 binding, because `fail_open` would have no effect. Otherwise the gateway accepts it in two other cases. When the entry omits `on_uninspectable`, `fail_open` still selects the [deprecated fallback](#handle-uninspectable-traffic) for uninspectable traffic. When the entry sets `on_uninspectable: allow`, `fail_open` matters to supervisors from releases before `on_uninspectable`. A policy stored before its middleware service moved to HTTP protocol 2 also keeps working. The entry's HTTP stages fail closed, and the sandbox supervisor emits a configuration event the first time the entry handles traffic in each direction under each policy version. The event is medium severity when no binding of the middleware honors `fail_open`, and informational when its WebSocket or HTTP protocol 1 bindings still do.

A supervisor learns which protocol each binding uses from the services' `Describe` responses. If any middleware service the supervisor needs is unavailable when it starts, the supervisor runs with built-in middleware only until it can describe every service. Until then, an entry that uses a registered service follows its `on_error` setting, except in each HTTP direction where the gateway described an HTTP protocol 2 binding when it started, which fails closed. The gateway sends those protocols to the supervisor with each service registration.

Some failures block the traffic whatever `on_error` says. If a service answers an HTTP middleware call from its manifest with gRPC status `UNIMPLEMENTED`, sends a message OpenShell cannot decode, or returns an HTTP protocol 2 result OpenShell does not recognize, OpenShell treats it as a contract failure. It fails the exchange closed, emits a high-severity `openshell.middleware.contract_failure` detection finding, and has the sandbox supervisor describe its middleware services again at its next policy poll. The supervisor reports the first contract failure of a service, binding, and kind at once, and summarizes later ones in one finding per policy poll with a `suppressed_count`. This catches a service that changed protocols behind the same endpoint.

A denial from middleware always blocks traffic, regardless of `on_error`. Middleware decisions also stay enforced when the endpoint uses `enforcement: audit`. To observe traffic without blocking it, have your middleware allow the traffic and report findings. An HTTP protocol 2 middleware can also let traffic it does not need to inspect continue at preflight.

`on_error` applies only to middleware failures. It does not extend what middleware can inspect, and the [current limitations](/extensibility/supervisor-middleware#current-limitations) apply under both settings.

## Handle Uninspectable Traffic

Some traffic that an entry selects cannot reach any middleware, such as connections to `tls: skip` endpoints, HTTP/2 prior-knowledge (h2c) connections, and other non-HTTP protocols. The `on_uninspectable` field decides what happens to it:

- `deny`, the default, blocks the traffic and emits a high-severity `openshell.middleware.traffic_uninspectable` detection finding. An entry with this setting cannot select a `tls: skip` endpoint.
- `allow` relays the traffic without inspection and emits a medium-severity `openshell.middleware.traffic_uninspectable` detection finding.

When several entries select the same host, OpenShell relays uninspectable traffic only if every one of them allows it.

```yaml showLineNumbers={false}
network_middlewares:
  content-guard:
    middleware: content-guard
    on_uninspectable: allow
    endpoints:
      include: ["*.example.com"]
```

<Note>

Earlier releases let uninspectable traffic through only for entries with `on_error: fail_open`. An entry that sets `on_error: fail_open` and omits `on_uninspectable` still allows it, and the sandbox supervisor emits a deprecation event each time it loads the policy. OpenShell 0.2.0 removes this fallback, so set `on_uninspectable` explicitly. An explicit `deny` takes precedence over `fail_open`.

Supervisors from releases before `on_uninspectable` ignore the field and reject a policy where an entry selects a `tls: skip` endpoint without `on_error: fail_open`. Until every sandbox runs a current supervisor, also set `on_error: fail_open` on entries that use `on_uninspectable: allow` for `tls: skip` endpoints, unless their middleware requires HTTP protocol 2. The gateway rejects `fail_open` on such middleware, and older supervisors cannot run it, so recreate their sandboxes before you attach it. On middleware with HTTP protocol 1 bindings, this also lets HTTP failures through. Remove it once those sandboxes are recreated, and before you upgrade to OpenShell 0.2.0.

</Note>

## Operate Middleware Services

Middleware services sit on the request path of every sandbox that uses them. Plan their availability accordingly:

- Start registered services before the gateway, and restart the gateway after changing registrations.
- Keep services available when creating or updating policies. The gateway asks the service to validate its `config` before it accepts a policy.
- Keep services reachable from sandbox supervisors, which call them directly for each request.

When a running sandbox receives a configuration change, its supervisor prepares the new middleware setup before using it. If it cannot connect to or describe a required service, it keeps its previous middleware setup and policy, emits a configuration failure event, and retries. If the new policy itself fails validation, the supervisor applies the gateway's [`policy_validation_failure_mode`](/how-it-works/gateways/configuration). The default, `fail_closed`, denies the sandbox's network traffic until a valid policy arrives, and `retain_last_valid` keeps the previous policy active.

### Change a Service's Protocol

The gateway and every sandbox supervisor call `Describe` separately. The gateway does so only at startup. A supervisor does so when it starts, when the set of middleware services it needs changes, and after a contract failure. After you deploy a service build that changes its HTTP protocol, restart the gateway so it reads the new manifest. `openshell gateway upgrade-check --to 0.2` lists registered services that still describe HTTP protocol 1 bindings to the gateway. [Upgrade to OpenShell 0.2.0](/upgrade/0-2-0) describes the check.

After a gateway upgrade, sandboxes can keep running a supervisor from an earlier release. Docker and VM sandboxes receive the new supervisor when the gateway restarts. Sandboxes on other compute drivers, such as Podman and Kubernetes, keep the supervisor they started with until you recreate them. Supervisors from 0.1.2 and earlier support only HTTP protocol 1:

- A service that serves both protocols works with every supervisor. Prefer it while sandboxes with older supervisors remain.
- Older supervisors refuse a service that requires HTTP protocol 2. Recreate those sandboxes before you switch the service to such a build. Until OpenShell 0.2.0, the gateway also rejects `on_error: fail_open` on entries that use such a service.
- Do not attach a service you plan to switch to an HTTP protocol 2-only build with `on_error: fail_open` while older supervisors use it. They keep the HTTP protocol 1 manifest they described, and under `fail_open` they skip the service when it no longer answers the HTTP protocol 1 calls.

[Migrate to HTTP Protocol 2](/extensibility/supervisor-middleware/migrate-http-v2) describes the service side of this change.

## Observe Middleware Decisions

OpenShell records middleware activity in its [OCSF logs](/observability/logging):

- Each invocation records the policy entry, middleware name, decision, whether it changed the traffic, and any failure.
- Failed middleware emits a detection finding, whether OpenShell blocks the traffic or skips the middleware. A contract failure also emits a high-severity `openshell.middleware.contract_failure` finding, at most once per service, binding, and kind for each policy poll of the sandbox supervisor.
- Coverage events record traffic that selected middleware could not inspect, such as WebSocket binary messages.
- Configuration changes emit state-change events on success and failure.
- Deprecated configuration emits medium-severity state-change events. The gateway reports each registered service that still describes HTTP protocol 1 bindings when it starts. The sandbox supervisor reports entries that rely on the `on_error: fail_open` fallback for uninspectable traffic when it loads a policy, and entries whose `fail_open` no longer applies to an HTTP protocol 2 binding when they first handle traffic. That last event is informational when the middleware's other bindings still honor `fail_open`.

For denials and findings, OpenShell logs the middleware name and a validated reason code or finding label. It does not log free-form text from your service. [OCSF JSON Export](/observability/ocsf-json-export) describes how to send these events to other systems.
