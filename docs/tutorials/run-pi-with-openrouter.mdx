This tutorial runs [Pi](https://pi.dev), a terminal coding agent, inside an
OpenShell sandbox. Pi works with many model providers out of the box. This
tutorial uses [OpenRouter](https://openrouter.ai), which lets you use models
from many companies with one API key.

You will build a Pi image, give the sandbox access to OpenRouter, and start Pi
inside it. Along the way, you'll see how OpenShell keeps Pi contained. The
sandbox lets Pi reach OpenRouter but nothing else on the network, and Pi never
sees your real API key.

## Prerequisites

- A working OpenShell installation with an active gateway. Refer to
  [Installation](/about/installation).
- Docker or Podman to build the image.
- An OpenRouter API key.

## Build the Pi Image

Pi doesn't publish a container image, so build one from its npm package. Save
this Dockerfile as `Dockerfile.pi`. It's based on Pi's
[container guide](https://pi.dev/docs/latest/containerization).

```dockerfile
FROM node:24-bookworm-slim

ARG PI_VERSION=latest

RUN apt-get update \
    && apt-get install -y --no-install-recommends bash ca-certificates fd-find git ripgrep \
    && ln -s /usr/bin/fdfind /usr/local/bin/fd \
    && rm -rf /var/lib/apt/lists/*

RUN npm install -g --ignore-scripts "@earendil-works/pi-coding-agent@${PI_VERSION}"

RUN mkdir -p /workspace && chown node:node /workspace
USER node
WORKDIR /workspace

ENV PI_CODING_AGENT_DIR=/tmp/pi-agent
```

This Dockerfile adds two things to Pi's container guide, because the sandbox
limits what Pi can reach:

- It installs `fd`. Pi uses `fd` and `ripgrep` to search files, and it
  downloads them from GitHub the first time it needs them if they're missing.
  The sandbox blocks that download, so the image includes both.
- It sets `PI_CODING_AGENT_DIR` so Pi keeps its settings and sessions in
  `/tmp`, one of the few places the sandbox lets Pi write.

Build the image:

```shell
docker build -t pi-agent:local -f Dockerfile.pi .
```

<Note>
If your gateway uses Podman, build with
`podman build -t localhost/pi-agent:local -f Dockerfile.pi .` and use
`localhost/pi-agent:local` in the commands below. If your gateway runs on
another machine, push the image to a registry the gateway can pull from, and
use that image reference with `--from`.
</Note>

## Give Pi Access to OpenRouter

A sandbox has no network access until you grant it. To let Pi reach
OpenRouter, create a provider. A provider stores your API key and opens access
to the service. Pi gets a placeholder instead of the real key, and OpenShell
swaps in the key only on requests to OpenRouter.

Each provider is based on a provider profile that describes the service. Save
this profile as `provider-openrouter.yaml`:

```yaml
id: openrouter
display_name: OpenRouter
description: Direct OpenRouter inference access
category: inference
inference_capable: true

credentials:
  - name: api_key
    description: OpenRouter API key
    env_vars:
      - OPENROUTER_API_KEY
    required: true
    auth_style: bearer
    header_name: authorization

discovery:
  credentials:
    - api_key

endpoints:
  - host: openrouter.ai
    port: 443
    protocol: rest
    access: read-write
    enforcement: enforce

binaries:
  - /usr/local/bin/node
```

The profile controls three things:

- `credentials` declares the API key. Pi finds the placeholder in
  `OPENROUTER_API_KEY`.
- `endpoints` allows only `openrouter.ai`, and OpenShell sends the key nowhere
  else.
- `binaries` allows only the `node` program to use this access. Pi runs on
  Node.js, so this includes Pi.

Check the profile, import it, and create a provider named `openrouter`:

```shell
openshell profile lint -f provider-openrouter.yaml
openshell profile import -f provider-openrouter.yaml

OPENROUTER_API_KEY=your-key \
  openshell provider create \
    --name openrouter \
    --type openrouter \
    --from-existing
```

Replace `your-key` with your OpenRouter API key, or drop that prefix if
`OPENROUTER_API_KEY` is already set in your shell. `--from-existing` reads the
key from that variable.

## Start Pi in a Sandbox

Create a sandbox from the image, attach the provider, and start Pi:

```shell
openshell sandbox create \
  --name pi \
  --from pi-agent:local \
  --provider openrouter \
  -- pi
```

The command after `--` starts Pi inside the sandbox. Any commands Pi runs stay
inside the sandbox too.

Pi starts with its default OpenRouter model. To choose a different one, type
`/model` in Pi and pick any OpenRouter model from the list. OpenRouter usually
offers some free models, marked with a `:free` suffix, that you can use to try
this setup without spending credits.

Then ask Pi a question:

```text
Explain what files are available in this workspace.
```

The workspace starts empty. A later step gives Pi your own code.

## Inspect the Sandbox

While Pi is running, open another terminal and check the sandbox's status, the
access it has, its providers, and its logs:

```shell
openshell sandbox list
openshell policy get pi --full
openshell sandbox provider list pi
openshell logs pi --tail
```

`openshell logs` streams the sandbox's activity, including any connections it
blocks. When you're done, type `/quit` in Pi to exit.

## Work on a Local Project

To have Pi work on your code, run this command from your project directory.
`--upload` copies the directory into the sandbox before Pi starts and skips
files that `.gitignore` excludes.

```shell
openshell sandbox create \
  --name pi-project \
  --from pi-agent:local \
  --provider openrouter \
  --upload .:/workspace \
  -- pi
```

Pi's changes stay inside the sandbox. To copy them back to your machine, run
`openshell sandbox download` from another terminal while Pi is still running.
Refer to [Transfer Files](/how-it-works/sandboxes/overview#transfer-files).

## Clean Up

Delete the sandboxes when you're finished:

```shell
openshell sandbox delete pi pi-project
```

## Troubleshooting

- If the gateway can't find `pi-agent:local`, build the image with the same
  container engine your gateway uses, or push it to a registry the gateway can
  reach.
- If Pi's requests to OpenRouter are denied, make sure the `binaries` path in
  the profile matches where `node` is installed in your image. In the image
  above, that's `/usr/local/bin/node`.
