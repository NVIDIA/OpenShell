Sandbox workload templates let workspace admins define reusable runtime shapes for a workspace. A template stores the image, environment, resource requests, and driver-specific configuration that sandboxes should inherit. When you create a sandbox from a template, the create request can still attach providers, labels, and policy, but the workload comes from the named template.

## Create a Template

```shell
openshell sandbox template create gpu-kata \
  --image registry.example.com/agent:latest \
  --cpu 2 \
  --memory 4Gi \
  --gpu 1 \
  --label team=runtime \
  --env FEATURE_FLAG=on
```

Use `--gpu` without a count when the template should request the active
driver's default GPU assignment. Use `--gpu COUNT` when the template needs a
specific number of GPUs.

For a separate template with driver-specific settings, create it with
`--driver-config-json`:

```shell
openshell sandbox template create gpu-kata-custom \
  --image registry.example.com/agent:latest \
  --driver-config-json '{"kubernetes":{"pod":{"runtime_class_name":"kata-containers","node_selector":{"pool":"gpu"}}}}'
```

If you omit `--image`, the gateway applies its default sandbox image when a sandbox is created from the template. Use this when the template should only define resource, environment, or driver settings.

## Request Warm Capacity

On a Kubernetes gateway with TLS and JWT signing, templates can request warm
capacity in managed, shared, or operator workspace mode:

```shell
openshell sandbox template create agents \
  --image nvcr.io/nvidia/base/ubuntu:24.04 \
  --ready-within 5s \
  --max-burst 2
```

Pooling is enabled by default. Both startup options must be present, with a
positive burst count. This template requests two unassigned runtimes using its
image, environment, resources, and driver settings. The gateway's per-template
capacity limit may cap that count. `--ready-within` expresses a desired startup
time; it does not guarantee that deadline.

Create with `--template agents` to use that capacity. An empty pool falls back to
cold creation. Deleting the template drains its unclaimed runtimes; it does not
delete sandboxes already created from it. Templates without startup tuning do not
create pools. Operators can disable pooling with
[`openshell.drivers.kubernetes.warm_pool.enabled`](/how-it-works/gateways/configuration).

### Identify Warm Pods

A warm Kubernetes Sandbox resource and its workload Pod use the physical name
`warm-<session-id>`. Claiming the runtime preserves both names and the Pod UID.
The dedicated supervisor Pod also keeps its original name. Use the Sandbox
resource's labels to find the logical sandbox created through OpenShell.

| Resource | Label | Meaning |
| --- | --- | --- |
| Sandbox | `openshell.ai/warm-pool` | Immutable template ID identifying the originating pool. Remains after claim. |
| Sandbox | `openshell.ai/sandbox-id` | Logical sandbox ID, added when the claim binds the resource. |
| Sandbox | `openshell.ai/sandbox-name` | Logical sandbox name, added when the claim binds the resource. |
| Sandbox | `openshell.ai/sandbox-workspace` | OpenShell workspace, present before and after claim. |
| Pod | `openshell.ai/boundary-pair` | Physical runtime pairing used by network policies. Remains unchanged at claim. |
| Pod | `openshell.ai/boundary-role` | `workload` or `supervisor` for dedicated runtime pairs. |

List resources originating from warm pools, including claimed sandboxes:

```shell
kubectl get sandboxes.agents.x-k8s.io -A -l openshell.ai/warm-pool \
  -L openshell.ai/warm-pool,openshell.ai/sandbox-id,openshell.ai/sandbox-name,openshell.ai/sandbox-workspace
```

An absent Sandbox `openshell.ai/sandbox-id` label means the resource has not yet
been bound to a logical sandbox. It does not prove that the runtime is ready or
available; preparation, reservation, or retirement may be in progress.

Use the namespace and physical name from that output to inspect the workload Pod.
Its boundary-pair value also selects its dedicated supervisor Pod:

```shell
kubectl -n <namespace> get pod <physical-name> \
  -L openshell.ai/boundary-pair,openshell.ai/boundary-role
kubectl -n <namespace> get pods -l openshell.ai/boundary-pair=<pair-value> \
  -L openshell.ai/boundary-role
```

On a dedicated supervisor Pod, `openshell.ai/sandbox-id` initially contains the
physical session ID and changes to the logical sandbox ID at claim. Use the
Sandbox resource for logical name and workspace lookup. A shared supervisor
serves multiple sandboxes and is not selected by a workload's boundary-pair label.

## Create a Sandbox from a Template

```shell
openshell sandbox create --template gpu-kata --provider github -- claude
```

The `--template` flag cannot be combined with inline workload flags such as `--from`, `--cpu`, `--memory`, `--gpu`, `--env`, or `--driver-config-json`. Put those values on the template instead. Create-time policy and provider attachments remain part of the sandbox request, so each sandbox can keep its own access boundary.

## Manage Templates

```shell
openshell sandbox template list
openshell sandbox template list --label-selector team=runtime
openshell sandbox template get gpu-kata
openshell sandbox template delete gpu-kata
```

Use `--all-workspaces` with `sandbox template list` when you need an admin view across workspaces:

```shell
openshell sandbox template list --all-workspaces
```

For JSON or YAML, template list output contains `templates` and
`next_page_token` fields. Pass the returned token to `--page-token` to
continue.
